## 만들 문서

| 문서 | 내용 |
|---|---|
| 아키텍처 | 기술 스택, 폴더 구조, 빌드 방식, 모듈 경계. 규칙(시뮬레이션)과 화면의 분리 방식 |
| 상태·데이터 스키마 | 저장 데이터 구조와 버전 관리, 정적 데이터 파일 형식 |

| 사건 시스템 | 사건 정의 형식(조건·선택지·효과), 교전 기회의 생성과 소멸 |
| 전투 | 전투력 계산, 승률, 결과 적용 |
| 화면 설계 | 화면·모달 목록, 반응형 기준, 컴포넌트, 디자인 토큰 |
| 저장 | 저장·불러오기, 가져오기·내보내기, 구버전 세이브 처리 |

## 설계가 반드시 다뤄야 할 것

- 한 기능의 규칙을 한 곳에만 둔다. 기존 함수를 덮어쓰는 방식의 확장을 금지한다.
- 사건의 효과를 저장 가능한 형태로 정의한다. 레퍼런스는 선택지 효과가 함수라서 저장했다 불러오면 진행 중인 사건을 복원하지 못한다.
- "전투 진행 중", "이야기 교전 대기 중", "항로 선택 가능" 같은 진행 상태가 어긋나지 않게 한다. 레퍼런스의 진행 불가 결함 4건이 모두 여기서 나왔다.
- 규칙 계산을 화면 없이 실행할 수 있게 한다. 검증 단계에서 자동 테스트와 대량 시뮬레이션에 쓴다.
- 수치(전투 계수, 확률, 보상)를 코드에서 분리한다.

## 완료 조건

- 기획서의 [동작] 항목과, 살리기로 한 미동작 항목이 모두 어느 모듈의 책임인지 정해져 있다.
- 저장 데이터 스키마가 확정되어 있다.
- 계획 단계에서 작업 단위로 나눌 수 있을 만큼 모듈 경계가 분명하다.
